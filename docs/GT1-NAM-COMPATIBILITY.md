# GT-1 and NAM A2-Lite compatibility assessment

**Status:** no native NAM execution path has been demonstrated; compatibility and full target resources remain unresolved. See [GT-1 execution-domain assessment](GT1-EXECUTION-DOMAIN-ASSESSMENT.md) for a bounded v1.08 CPU/DSP census and its limitations.  
**Scope:** replacing one GT-1 amp-model stage with TONE3000 A2-Lite while retaining the GT-1's audio hardware and remaining effects.  
**Evidence cutoff:** 2026-11-03.

**Connected device baseline:** user-reported GT-1 firmware v1.08; it matches the local v1.08 package but the firmware itself was not read back. A documented raw SysEx user-data backup includes system settings and all 99 user slots. The raw capture is `backups/gt1-2026-11-03/gt1-user-data.syx`, with complete-frame/checksum validation and patch index in the backup folder.

## Assessment

There is not enough evidence to call the GT-1 compatible or incompatible in the abstract. The uploaded GT-1 service notes establish that the MB8AA4181 (ESC2) is directly wired to the AK4556 codec's serial audio data/clock pins and both external SDRAMs, making ESC2 the leading amp-processing target. A bounded v1.08 code census found no VFP/NEON or listed Armv7E-M DSP instructions in the scanned slices, but it covers only part of one copied segment and does not establish the complete CPU feature set. Firmware also exposes DSP program/data controls, but no boot-time audio-engine load or amp callback has been tied to them. Exact ESC2 execution features and clock, memory/bus performance, replaceable amp-stage contract, and worst-case audio deadline remain open. The service notes' 48 MHz CKCPU label is a board reference, not a confirmed core clock. See [GT-1 execution-domain assessment](GT1-EXECUTION-DOMAIN-ASSESSMENT.md) for the bounded result and its limitations.

Current evidence supports plausible **raw memory capacity**, not allocatable or real-time usable memory. Compute remains a major concern: the published A2-Lite benchmark is for a 480 MHz Cortex-M7 path; neither the relevant GT-1 core clock nor target performance is established. The pinned upstream README describes FPv5/Thumb-2 optimized kernels and a C fallback without target timing. The partial v1.08 scan found no VFP/DSP instructions in its inspected slices, but does not prove the complete app or core lacks these features. The schematic places ESC2 directly on the codec serial-audio interface and external memory buses. Inference: the recovered M-profile app runs on that audio-connected ESC2. Separate firmware diagnostics identify DSP program/data controls, but do not show which domain executes amp processing. Any 48 MHz compute comparison is conditional on CKCPU being the actual core clock and on comparable cycles/sample; neither is established.

## Quantitative bounds (not measurements)

- Published M7 work at 44.1 kHz: `4,059 × 44,100 = 179,001,900 cycles/s` (about 4,059 cycles per sample).
- Published M7 work at 48 kHz: `4,059 × 48,000 = 194,832,000 cycles/s`.
- At a hypothetical 48 MHz single core, the 48 kHz published-rate-equivalent workload is 4.059 times the full core budget before resampling, other effects, interrupts, or system work. At 44.1 kHz straight-rate arithmetic, it is 3.729 times the budget, but direct 44.1 kHz processing is not the documented engine configuration.
- The required rate ratio is `48,000 / 44,100 = 160 / 147`. A valid pipeline needs conversion into the NAM rate and back to the GT-1 rate unless the engine/model is adapted and revalidated at 44.1 kHz. No conversion-filter cost or latency is included in the figures above.
- The block-48 state is about 100.1 KiB; upstream's rounded hot instance plus weights is 9.2 KiB; engine code is about 12.4 KiB. These do not include the rest of the effect chain or the GT-1's allocation overhead. Comparing them with 24 MiB nominal SDRAM does not establish fit.
- The PRAM self-test checks candidate windows of 32 KiB (`0x2000` 32-bit reads) and 6 KiB (`0x300` 64-bit reads) per selected bank. These loop extents are not full-memory size measurements or evidence those banks are available to NAM.
- The upstream Cortex-M7 benchmark harness was built and run on the host against the pinned A2-Lite `.namb` capture. Its correctness check passed (`48` samples, maximum absolute error `74e-9`, threshold `32718e-9`). The executable also printed a host-derived “cycles/sample” figure; upstream states that host timing is not meaningful, so that number is deliberately excluded from all target feasibility calculations.

## Newly reproduced M-profile evidence

The bounded probe `firmware/work/scripts/reproduce_gt1_startup_mprofile_probe.py` prints hash-checked disassembly and resolves PC-relative literals from the reconstructed first-copy segments. It verifies v1.08 segment SHA-256 `5691f04c08e52373973725ede20ff9de0bc3fc0e77a160e856a11342701168a0` and app SHA-256 `c41319e5f5a1facd5e55fe2c8e56d37069e31b98e5034d6d54d932fa7713e8c1`; v1.09 segment SHA-256 `019adcf28e4a12444d48699b0b2a386a1a5feb2e43b59d465c696ee42540b9f9` and app SHA-256 `2028d7e1f8a72e54b23a80427f53ba27629a7039a72712504a612c877556aa29`.

In v1.08 startup at `0x010010AE` calls a ratio/remainder initializer at `0x010020A4`, iterates the 14-entry startup callback array, then calls `0x0100468C`. In v1.09, corresponding addresses are `0x0100114E`, `0x01002144`, and `0x01004728`. The initializer loads a descriptor pointer, divides its first 32-bit value by the second with `UDIV`, calculates the remainder with `MLS`, and stores both results in an object. Its semantic role is unknown.

Both vector/SVC setup functions load `0xE000ED08`, load `0x01000000`, store the latter to the former, call a Thumb handler, then execute `SVC #0`; a neighboring wrapper executes `SVC #1`. The adjacent helpers read and write `BASEPRI`, including setting it to `0x80`, which is consistent with interrupt-priority masking. This materially strengthens the ISA-family evidence and supports targeting an ARM M-profile C fallback if a usable toolchain is found. It still does not establish that the audio algorithm executes on this core, whether a separate accelerator exists, or whether floating-point instructions are supported or used. Neither the divider object nor the system-call wrappers have yet been connected to audio-buffer scheduling.

## Execution-domain distinction to resolve

The application also contains a diagnostic-string cluster for `CPrmESC2DT1`, including errors for “PRG Set without DSP Halt” and “DRP Set without DSP Halt.” A bounded SysEx path classifies and stages transfer requests, then dispatches program/data transfer helpers using candidate registers around `0x40100000`. This is evidence of firmware code that knows about DSP program/data operations. Current static work does **not** prove these operations load the audio engine during boot or patch changes, that a separate processor core exists, or that amp algorithms execute in that domain. It does mean the next compatibility decision must identify which execution domain runs the amp model. If the app processor controls a separate DSP, a portable NAM C build for the app's M-profile ISA would not itself establish a replacement path for that DSP.

A new hash-pinned Thumb-2 call-reference scan sharpens this distinction. It finds the SysEx receive-state function calling the transfer parser, and the parser calling its staging/flush chain. The pinned scan was rerun against the decoded v1.09 image (SHA-256 `2028d7e1f8a72e54b23a80427f53ba27629a7039a72712504a612c877556aa29`): it finds no direct call or aligned absolute pointer to the receive-state function elsewhere in the image, so its registration/caller remains unknown. The parser’s stager calls are at `0x6007E310`, `0x6007E33E`, `0x6007E3B0`, `0x6007E3E0`, `0x6007E40E`, and `0x6007E438`; flush-dispatch calls are at `0x6007E23A`, `0x6007E2E6`, and `0x6007E386`. The shared low-level transfer helper also has direct callers at `0x600080F0`, `0x60008118`, `0x60046460`, `0x6004648A`, and `0x6004679C`. Follow-up disassembly places `0x600080F0` and `0x60008118` inside the selector-driven test dispatcher at `0x60007E1C`; its table routes selectors 2 and 4 to paired calls through wrapper `0x60046426`. The `0x6004679C` caller belongs to the PRAM test described below, and the `0x60046460`/`0x6004648A` callers lie in the same bounded test-oriented helper region. These transfer-helper references currently support SysEx/control and diagnostic-memory-test routes; none provides a boot-time engine-load or live audio/amp-model path. Reproduce with `firmware/work/scripts/reproduce_esc2_transfer_callrefs.py` and `firmware/work/scripts/reproduce_esc2_memory_test_probe.py` against the pinned v1.09 app. The scan explicitly does not rule out indirect or relative-table dispatch.

The caller at `0x6004679C` belongs to a candidate internal-memory test at `0x600466E2`. Two wrapper paths call that routine with selectors 0 and 1, and set failure bits `0x40` and `0x80`. A common result formatter maps those bits to entries 2 and 3 of a pointer table containing `NG (PRAM0)` and `NG (PRAM1)`. The tested code selects `0x40150000`/`0x40170000` for 0x2000 word reads and `0x4014E000`/`0x4016E000` for 0x300 doubleword reads, then calls shared transfer helpers. This is stronger evidence for distinct PRAM bank test paths and addresses; it still does not say the regular amp algorithm runs there, or that the tested ranges are full bank sizes. Reproduce using `firmware/work/scripts/reproduce_esc2_memory_test_probe.py`.

The same probe includes the upstream dispatcher at `0x60007E1C` and its test callers. Its `TBB` table has selector 0 targeting `0x6000802C`; selectors 1–5 reach `0x60007E36`. That path distinguishes selectors 2 and 4 and calls the paired memory-test wrapper. Callers at `0x6007D8D8` and `0x6007D8F2` invoke the dispatcher inside a small state-table handler. This supports classifying the nearby transfer-helper callers as test/control paths, not normal audio processing. The bounded trace does not establish the enclosing handler's user-visible role or the complete test-menu linkage.

The task-management code traced at relocated addresses `0x01001230` and `0x010035B0` is an event/task queue path: it inspects readiness flags, detaches and reinserts linked task records, and eventually enters a wait loop through `0x01002A78` and `0x0100466E`. This confirms that the first `initial task` handler is part of OS-style task control, not evidence of an audio callback. Its underlying wait/dispatch service implementations and callback registrations remain unresolved. The available bounded startup reports show no recurring audio buffers, codec/DMA work, floating-point audio kernels, or amp-model dispatch; that is a bounded negative result, not a whole-image proof. The reachable app code does show Thumb-2 M-profile operations, but contains no demonstrated FPU enable sequence or floating-point instruction in these startup/task traces. Therefore the ESC2 floating-point capability and A2-Lite execution domain are still unproven.

## Parallel-track execution-domain result (2026-11-03)

A hash-pinned v1.08 census and its limitations are documented in [GT-1 execution-domain assessment](GT1-EXECUTION-DOMAIN-ASSESSMENT.md). It narrows the execution-domain question without resolving it: partial application slices show Thumb integer instructions and no observed VFP/DSP instructions; DSP program/data controls and IRAM/PRAM names are present; but full ISA/clock coverage, audio ownership, and native NAM fit remain unknown.

- **Firmware-edit side:** the v1.09 application is decodable and re-encodable in its own LZ format; an offline no-op repack round-trips byte-for-byte at 1,181,994 bytes (capacity 1,818,560) with a corrected header and checksum. The updater contains sum/header/verify/compare error strings, so ARM-side application edits are plausible once the exact updater/bootloader checks and a recovery plan are settled. This does not create a native NAM path. See [GT-1 firmware editing assessment](GT1-FIRMWARE-EDITING-ASSESSMENT.md).
- **Practical route:** the GT-1's documented USB audio path (`EFX OUT` to computer, `USB IN`/`MIX LEVEL` return, `DIRECT MONITOR` off for through-monitoring) supports external host-side NAM. It is a post-effect arrangement, not a replacement at the internal amp stage.

This does not prove that no DSP re-engineering could ever run a NAM-like model. It establishes that no native NAM execution path has been identified; the CPU census is partial, and the DSP route requires primary ISA/toolchain evidence and a target audio contract before feasibility can be judged.

## What would settle compatibility

1. **Continue reachable firmware tracing.** The v1.09 startup callback array is resolved as 14 Thumb entries, and bounded bodies show task, pool, list, and descriptor initialization; no entry yet identifies recurring audio work. The `0x6007E1F2` receive/parser route and its test/control transfer callers are partly mapped, but its registration and any boot/audio use are unknown. Trace indirect callback/provider tables and pointers used by candidate codec/audio setup, and identify a direct recurring call/data route into amp/preamp implementation or state the exact static-analysis boundary. The decoded v1.09 app image is now present at firmware/work/decoded/v109-GT1Appli.bin under the canonical project root. Prioritize the next device session below before expanding static analysis.
2. **Find amp execution and its contract.** Identify whether audio processing runs on the M-profile app path or a separate DSP/program-memory execution domain. Trace any PRG/DRP loading or control path into recurring audio processing; establish buffer format/size/channels, scheduling cadence, amp/preamp dispatch, state/scratch ownership, and the replaceable stage. Link patch PREAMP controls only after runtime reachability is established.
3. **Identify the audio execution target.** Obtain GT-1-specific MB8AA4181/ESC2 programming or toolchain documentation, or another defensible direct source for the app and audio-execution domains, ISA/core features, clocks, memory map, and compiler support. Treat related-product schematics and ARM-compatible startup decoding as supporting clues only.
4. **Measure target resource fit.** Build the portable A2-Lite path for the confirmed target, verify output against the reference, and measure worst-case cycles/time per audio block, code/state/stack/scratch size, and memory/bus behavior. Include rate conversion and the remaining GT-1 effects in the deadline.
5. **Decide the integration route.** Confirm whether the amp stage can be substituted in firmware and define reset/bypass/model-load behavior. Do not write or flash firmware as part of static analysis; a later hardware experiment needs separate scope because documented update interruption can require service.

The current static-analysis boundary is now explicit: the recovered startup and task code establishes M-profile task/event management, while the transfer routes found so far are SysEx/control and diagnostic memory-test paths. Neither side reaches an identified live audio callback or amp implementation. Further general OS queue tracing has low value until it is tied to audio registration. The next software work should target indirect callback/provider tables and code references from codec/audio-related state; if those remain opaque, the smallest decisive evidence source is GT-1-specific ESC2 programming documentation or a safe, read-only trace/firmware map from the device.

## Smallest useful GT-1 bench evidence set

Once the GT-1 is physically available, keep the first session non-invasive and record:

0. **USB baseline:** connect with BOSS TONE STUDIO, record the system firmware version, and back up user patches/settings. This is a baseline and patch backup, not a firmware readback; the official update image is already available locally.

1. **Identity and debug boundary:** firmware version and PCB revision; inspect only whether the unpopulated JTAG/trace pads are actually present and whether a documented read-only attach method exists. Do not infer signals or drive an unknown header. An attach that can halt the audio core is not passive, so require an explicit safe procedure before trying it.
2. **Audio contract:** observe codec serial clock/frame/data lines with high-impedance passive probes, if suitable equipment is available, and infer sample rate, bit depth, slot/channel count, and whether data is continuous. This confirms the physical stream but not internal DSP block sizes or the amp-stage API.
3. **Execution-domain evidence:** obtain a read-only processor/debug identification and trace or profile the running code only if a vendor-supported non-halting method exists. If no safe trace path exists, use GT-1-specific ESC2 documentation or a preserved linker/runtime map; avoid exploratory SysEx writes or firmware changes.
4. **Resource timing:** only after the execution core and a safe measurement interface are established, benchmark a standalone NAM block with representative memory placement and include conversion cost. Compare worst-case per-block time against the actual audio period and inspect memory/bus contention; do not run experimental NAM inside the stock signal path.

This sequence can verify the board-level stream and whether a safe execution trace is possible, but it cannot prove an amp replacement point by itself. That still requires firmware control-flow evidence or a separately authorized reversible integration experiment.

## Current decision

**No native NAM-on-GT-1 path is demonstrated; compatibility remains unresolved.** The v1.08 CPU census is too partial to establish that the full application or core is integer-only, and the DSP program/data evidence does not identify which domain executes the amp algorithm. The stock A2-Lite engine has no demonstrated target build, loader, or benchmark for either domain. The USB route enables external host-side NAM after the GT-1 effects chain; it does not insert NAM at the amp block.

A stronger native decision requires more complete coverage of the relevant v1.08 execution regions, a confirmed clock, evidence linking CPU or DSP work to recurring audio and the amp stage, and a target benchmark. Primary ESC2 DSP documentation or a working toolchain would be needed before pursuing a DSP port.
