# GT-1 firmware research plan: NAM feasibility and custom amp voices

**Updated:** 2026-11-03  
**Status:** Active; verified backup, read-only host enumeration, and static firmware analysis  
**Goal:** Two linked questions. (1) Can one existing GT-1 amp-modeling stage be replaced or augmented by NAM A2-Lite while retaining the processor's hardware and effects? (2) Can the amp engine the pedal already ships be retuned into new voicings without new DSP code? Compatibility is unproven in both cases.

The current evidence-based compatibility assessment is maintained in [GT-1 and NAM A2-Lite compatibility assessment](GT1-NAM-COMPATIBILITY.md). The second question is tracked separately in [GT-1 amp parameter track](GT1-AMP-PARAMETER-TRACK.md).

## Parallel-track checkpoint — execution domain (2026-11-03)

A hash-pinned v1.08 census found no VFP/NEON or listed Armv7E-M DSP instructions in a strict linear prefix covering 21.0% of one startup-copied segment, and no such instructions in a narrow direct-edge walk covering 4.8%. The walk begins at startup entries and pinned callback targets but omits conditional and indirect control flow. The decoded application has no exact CPACR literal. These results do not prove the whole application or core is integer-only. The v1.08 app also carries ESC2 DSP program/data windows, transfer controls, and `IRAM`/`PRAM` diagnostics, but no amp execution path or boot-time DSP load is established. Details and reproduction are in [GT-1 execution-domain assessment](GT1-EXECUTION-DOMAIN-ASSESSMENT.md).

**Program-load reachability checkpoint (2026-11-03).** The FA-08-style DSP program loader is present in the GT-1 application in identical structural form but is unreachable in v105, v107, v108, and v109: the PRAM0/PRAM1 block transfer has exactly one external caller, whose enclosing function has zero external incoming edges. Only two occurrences each of `0x40150000`/`0x40170000` exist in the whole image, both inside that dead path, and the updater has none. The live `0x60058xxx` command-register path does write DSP address space (26 sites), so runtime traffic is parameter/data, not program. This materially strengthens the mask-ROM hypothesis but does not prove it: the runtime `0x02003xxx` service table, RAM-resident pointers, and any boot stage outside `GT1Appli` remain unresolved. Reproduce with `firmware/work/scripts/reproduce_gt1_dsp_load_reachability.py`; output `firmware/work/gt1-dsp-load-reachability.json`. Note also that the addresses previously recorded as DSP helpers (`0x60056BFE`, `0x60056D06`) are mid-function instructions, not function entries.

**Amp parameter track (2026-11-03).** Because the DSP program-load path is unreachable, the application-to-DSP traffic that remains is parameter/data. A separate track, [`docs/GT1-AMP-PARAMETER-TRACK.md`](GT1-AMP-PARAMETER-TRACK.md), targets new amp sounds on the unchanged DSP by driving and editing that parameter surface. Each preamp slot carries 30 fields including a full cabinet, mic and `custom_*` voicing set; the image ships plaintext parameter records on a uniform `0x753` stride (310 candidates, 308 on-stride, spanning `0x199D7C`–`0x25ECB1`), and a `{pointer, 0x9F, 0x63}` descriptor in the `0x20000000` data segment is the best clue to the index table. The decisive open question is whether a TYPE selection sends an identifier or a full parameter block. Reproduce with `firmware/work/scripts/reproduce_gt1_amp_record_scan.py`.

Consequence for the roadmap: prioritize the audio contract and amp-stage boundary, then identify which CPU/DSP domain executes it. The 48 MHz `CKCPU` compute comparison is conditional and no target benchmark exists. Host-side NAM is an external post-effect route, not an internal stage replacement. The native fit remains unresolved pending full v1.08 target evidence and a target-specific benchmark.

The firmware-edit side is also partly demonstrated offline: `firmware/work/scripts/reproduce_gt1_app_repack.py` decodes the v1.09 app, re-encodes it in the same LZ format, and produces a byte-exact round-trip at 1,181,994 bytes (capacity 1,818,560), with a corrected `+0x30` length and `+0x34` additive checksum. The updater contains explicit sum/header/verify/compare error strings, so the remaining gate is the exact updater and bootloader validation plus recovery, not the container format. See [GT-1 firmware editing assessment](GT1-FIRMWARE-EDITING-ASSESSMENT.md). This makes ARM-side application customization the realistic firmware target; it does not create a native NAM path.

## Decision-oriented roadmap

The project has two linked questions: **where and how does the GT-1 execute amp models?** and **can NAM A2-Lite meet the hardware, timing, memory, and integration constraints at that point?** Work in the order below. Keep each conclusion tied to reproducible evidence; a promising address or a successful host build is not a feasibility result.

### Gate 1 — Find the amp-model execution path

1. The reachable pre-callback register comparison and M-profile startup probe are reproduced. The v1.09 SysEx receive-state candidate `0x6007EA96` directly calls parser `0x6007E1F2`; the parser stages address/value pairs at `0x60094F24`, and flush handling at `0x6007E0E0` calls indirect transfer operations that reach the `0x40100000` register window. Known direct callers of the shared low-level helper include PRAM0/PRAM1 tests, but no caller yet links the mechanism to boot-time audio-engine loading. The receive-state registration is still unresolved. A separate address-catalog path links nine range descriptors and a 0x89A-entry lookup array to bounded parameter/key helper callers; it still does not identify audio execution. Resolve whether this M-profile app owns audio or controls a separate DSP program/data interface; do not infer core ownership from the app ISA alone.
2. Map startup callback callees and the relevant `0x020030B4` dispatch slots back to their table provider/initializer. Follow the path from boot through audio-device setup and the first recurring audio work, rather than continuing to inventory unrelated transfer code.
3. Identify the audio data flow: converter/interface setup, interrupt or task cadence, DMA or buffer handoff if present, sample rate, block length, sample format, channel count, and buffer ownership. Find the code that dispatches amp/preamp algorithms and the boundary between amp modeling and the rest of the effect chain.
4. Correlate candidate code/data with official GT-1 parameter semantics and patch-level PREAMP/chain controls. Use cross-version matches and call/data xrefs to distinguish actual amp execution from UI, preset, editor, or diagnostic code.

**Gate 1 exit evidence:** a call/data path from a recurring audio callback (or equivalent processing loop) into an identified amp-model implementation, plus the buffer contract and the point where that stage can be selected or replaced. If static analysis cannot establish this, state the unresolved hinge and identify the smallest safe next evidence source (e.g. primary ESC2 documentation or an explicitly approved bench observation); do not claim a tap point.

### Gate 2 — Establish the target and resource budget

1. Confirm the app processor and audio-execution core/ISA separately, including whether a distinct DSP program/data domain exists and how firmware loads or controls it. Establish compiler/runtime features for the actual amp-model target from GT-1-specific evidence; keep generic Thumb decoding and related-product ESC2 clues as bounded evidence only.
2. Map the memory actually visible to the audio code, separating code, model weights/capture, persistent state, stack, audio buffers, and existing effect workspace. The v1.09 startup stub copies all nonempty code/data segments out of candidate `0x60000000` storage, clears the overlapping source region and about 1.78 MiB beyond the decoded file at `0x602BADF0–0x604816B8`, then branches to relocated code. This strongly suggests reclaimed staging/workspace, but physical chip mapping, allocator ownership, aliases, and audio access remain unproven. Resolve these against ESC2 memory documentation and firmware consumers before counting the area as NAM headroom; do not treat zeroing or nominal capacity as free/usable memory by itself.
3. Recover the audio deadline and contention constraints: cycles or time per block, interrupt priority, memory traffic, and any shared accelerator/DSP use. Establish these from firmware or target measurements only when the required measurement is authorized.
4. Resolve the 44.1 kHz integration requirement. Determine whether a 44.1 kHz NAM model/engine path is practical or whether resampling is needed, then budget its cost and latency alongside the GT-1's existing chain.

**Gate 2 exit evidence:** a defensible target build profile, memory budget, and worst-case per-block time budget with explicit unknowns. If core features, memory headroom, or deadline cannot be bounded, NAM feasibility remains unproven and implementation should not advance to firmware integration.

### Gate 3 — Test NAM compatibility away from the GT-1 firmware

1. Pin the exact A2-Lite source/model format and inspect whether the engine can be built for the confirmed target without unsupported instructions, floating-point assumptions, or oversized library dependencies.
2. Build a minimal standalone harness for the confirmed ABI. Measure code size, static/state memory, stack high-water mark, and worst-case processing time on the target or a cycle-accurate-enough equivalent. The existing upstream host harness passes a 48-sample A2-Lite correctness check, but its host timing is explicitly not meaningful; host timing is useful for correctness only.
3. Test representative captures and worst-case input levels, including startup/reset, denormals or other numeric edge cases where relevant, and repeated block processing. Compare output against the reference engine within a stated tolerance.
4. Run the engine at the GT-1's actual sample/block contract. Compare native 44.1 kHz handling against resampling, including CPU cost, latency, and audible/output error.

**Gate 3 exit evidence:** reproducible target-specific build and benchmark results show that the engine and at least one useful model fit the code, RAM, stack, and deadline budgets while meeting the required output tolerance. If not, test one clearly scoped optimization or smaller model, then record a no-go if the budget still fails.

### Gate 4 — Prove the integration boundary and make a go/no-go decision

1. Specify the replacement interface: input/output buffers, ownership, parameter handoff, bypass/failure behavior, sample-rate conversion if any, and how the rest of the GT-1 chain remains scheduled.
2. Estimate integration cost and risk separately from DSP feasibility: patch/firmware access, boot integrity, update recovery, and reversibility. Keep static evidence work separate from any hardware write or flash experiment.
3. Decide among **feasible in principle**, **feasible with constraints**, **not feasible on the existing execution path**, or **still unknown**. State the evidence supporting the decision and the single next experiment that could change it.

No firmware modification or flash experiment is part of this plan. Any such work is a later, separately scoped phase because the documented update failure mode can require service.

## Current position

The transfer/control path now has a reproducible protocol and four-version code comparison. The uploaded service notes establish board-level topology: ESC2 connects directly to codec serial audio and external SDRAM. A bounded v1.08 SysEx path stages target-addressed values and uses shared ESC2 transfer helpers; diagnostic PRAM tests also use those helpers. This proves an app-to-ESC2 program/data control facility, but current evidence does not connect it to boot-time DSP loading or amp processing. The app's reachable pre-callback initialization at `0x600004A8` and direct callees write several `0x400xxxxx` blocks before the 14-entry callback loop; subsystem identities remain unknown. No recurring audio callback, buffer contract, or amp-model dispatch path has been recovered.

The decoded app's second startup entry reaches `0x600004A8`. That routine loads `0x020030B4` as a base and makes indirect calls through offsets `-0x5C`, `+0x58`, `+0x70`, and `+0x7C`; the same route and call slots are confirmed in v1.08 and v1.09. Both versions call this dispatch before their 14-entry initialization callback loops. Four Thumb literal-load references in the bootstrap load base `0x02003000`, then call through offsets `+0x0C`, `+0x14`, `+0x18`, and `+0x58`. Ghidra call xrefs place these functions on the loader path: `0x010002CA` transfers to loader entry `0x010009F0`, which calls `0x01000B5E` and `0x010006D0`; `0x01000B5E` reaches `0x01000888`, which calls `0x01000862`. The bootstrap `+0x58` slot is exactly the app's `0x020030B4-0x5C` slot. GT-1B v1.04 has byte-identical code across bootstrap file offsets `0x700–0xBFF` and matching Ghidra references/call edges, supporting a shared boot interface. The inspected service-call function bodies dereference slots but do not directly write the table; a separate byte-copy helper exists in the loader, but its source/destination have not been tied to this table. Therefore the table's physical meaning, provider, initializer, and values remain unknown. A second app code sequence at `0x60000446` and an updater sequence at `0x60003ED2` also load `0x02003000` and call through `+0x0C`; startup reachability for these sites remains unproven. The app callback slots spanning `0x02003058` through `0x02003130` are outside startup ranges mapped so far.

In v1.09, the reachable route continues through `0x60000302`, `0x60000342`, `0x6000039E`, `0x6000046A`, and `0x60000440`. Its literal pool at decoded offsets `0x500–0x53C` includes `0x40007804`, `0x40025000`, `0x4002E000`, `0x40021184`, `0x4002D000`, `0x4002D800`, and `0x40023000`. Disassembly shows bit updates at the first group, writes through offsets `0x00/0x10/0x18/0x20/0x28/0x30` at `0x4002D000`, and configuration writes to `0x4002D800` and `0x40023000`. This is a reachable peripheral-initialization candidate. The addresses and ordering are observed; labels such as clock, audio, DMA, or codec are not established. The indirect targets from the `0x020030B4` slots remain unresolved. Check the v1.08 body instruction-by-instruction before treating the register writes as version-stable.

Ghidra 12.2 analyzes bounded copied regions as ARM Thumb-compatible code (`ARM:LE:32:v7`, Thumb context). This supports the ISA for those reachable paths only; it does not identify the exact MB8AA4181 core or prove its FPU, DSP extensions, clock, or full application ISA. The service notes document ESC2's codec and external WORK/ERAM connections and nominal capacities, but not available bandwidth or free memory. The block diagram labels a 48 MHz clock source/reference as CKCPU; treat this as a board clock clue, not a verified post-PLL core frequency.

The pinned TONE3000 A2-Lite implementation documents a 48 kHz engine and an upstream optimized Cortex-M7 result of 4,059 cycles/sample. GT-1 is documented at 44.1 kHz. These figures are comparison points, not GT-1 performance evidence. Neither compute fit nor a usable amp-block interface has been demonstrated.
