# BOSS GT-1 firmware and NAM feasibility

**Status:** static reconnaissance only; no device was connected or modified.  
**Date:** 2026-11-03.  
**Evidence labels:** **Verified** means supported by a BOSS/Roland or upstream primary source inspected for this report. **Reported** means observed in a third-party analysis, not reproduced here. **Hypothesis** means an engineering inference awaiting a dump or hardware test.

## Executive summary

The currently offered official update is GT-1 System Program v1.09. BOSS documents a USB mass-storage-style updater that copies `ROMINFO.TXT` and `GT-1ROM.BIN` to the pedal while it is in updater mode, then asks the user to start the update on the device. BOSS warns that interrupting power can leave the unit unable to start normally. The official page lists v1.08 (March 2018), v1.07 (June 2017), v1.05 (October 2016), and v1.09 (December 2021, management-only version change).

The main processor is identified in service documentation as Roland/BOSS ESC2; its `MB8AA4181` marking on the GT-1 is community-reported. Static parsing of all four images identifies a 32-bit additive checksum over each stored updater/application payload, but whether the updater validates it is unknown. Public documentation inspected here does not specify its instruction set. Related AD-10 documentation identifies the same ESC2 part and labels SWD/SWV-style debug/trace signals, making ARM Cortex-M a credible family hypothesis, but this is not GT-1-specific proof. Locally reproduced disassembly finds coherent ARM Thumb/Thumb-2 code in bounded bootstrap regions of GT-1 `ESC91.000`, FA-08 `ESC90.000`, and KATANA `ESC91.000`. The GT-1 bootstrap also contains a 176-word Cortex-M-style vector table whose nonzero handlers are Thumb pointers into that block; KATANA v2.01/v4.00 show the same structure. The GT-1 and FA-08 24-byte init-table loops are byte-identical; KATANA v2.01/v4.00 reset vectors and startup trampoline also agree under the candidate `0x00FFFFD0 + file_offset` mapping. Ghidra independently decodes the FA block using built-in ARM Cortex language. This strongly supports Cortex-M-style bootstrap code, but does not prove those blocks execute on the MB8AA4181, nor establish the ISA/load map of the later GT-1 `GT1Upd` and `GT1Appli` payloads. The application ISA therefore remains unknown, and ARM import for those payloads is not yet justified.

Reachable application startup paths now identify an object named `initial task` and objects named `stack pool` and `general pool` in both v1.08 and v1.09. Callback/helper analysis shows linked-list and pool-object initialization, but does not identify a specific RTOS, the audio task, or the converter/DMA callback. This is a firmer runtime-software lead than the earlier generic registry hypothesis; the amp-model integration boundary remains unresolved.

The startup route also performs a stable set of pre-callback writes to `0x400xxxxx` address blocks in v1.08 and v1.09. A register-update helper writes descriptor-selected byte lanes through `0x4002D400`. These are now documented at instruction/dataflow level, but remain unnamed peripheral accesses and are not yet evidence of audio initialization.

**MB8AA4181 documentation search (2026-11-02):** Exact-part searches did not locate a public Fujitsu/MBI datasheet, programming manual, patent, or instruction-set reference. The most concrete accessible evidence remains Roland/BOSS service-note schematics: they call the part `MB8AA4181(ESC2)` and expose external SDRAM, serial flash, audio serial, and control-signal connections in multiple products. A SH-01A service-note OCR, for example, shows ESC2 clock, SFI, SDRAM, codec/I2S-type signal names, but these interface labels describe that product's board wiring and reveal no instruction set. The FA-08 and KATANA schematics provide boot/debug/trace labels discussed below, again without a core manual. Roland's public product/community copy calls ESC2 a proprietary DSP, which identifies the marketing role, not its ISA. Component-marketplace listings and forum guesses about ARM, H8, RISC, or a custom core are not treated as architecture evidence. This negative search result does not prove that no private or non-indexed documentation exists. Primary located references: [BOSS GT-100 community description of ESC2](https://www.boss.info/us/community/boss_users_group/1632/), [FA-08 service-note scan](https://manualmachine.com/roland/fa08/9252142-service-notes/), [SH-01A service-note scan](https://www.scribd.com/document/730805467/SH-01A), and [the direct GT-1 reverse-engineering discussion](https://www.linux.org.ru/forum/talks/17651382).

**Adjacent Roland encryption-pattern comparator:** A 2026 independent [TR-6S/Cowbell reverse-engineering article](https://averywagar.com/post/tr6s-part1/) reports a distinct BMC-based platform with a 96-byte plaintext `App1_Main` header, encrypted body, plaintext build trailer, and a high repeated 8-byte-block rate interpreted as an ECB-like encryption clue. The author explicitly describes a custom BMC SoC rather than MB8AA4181/ESC2; this result must not be transferred to GT-1. As a comparative falsification probe only, we measured exact fixed-block repeats in the bounded GT-1 payloads. Across v1.05/v1.07/v1.08/v1.09, the updater payload has zero repeated aligned 8-byte blocks. The application payload has 2.02%–2.15% of aligned 8-byte blocks participating in repeated groups (largest group 5–7 copies), versus about 30% reported by that article for its TR-6S body. At 16-byte alignment, GT-1 app duplicate participation is about 0.18%–0.27%. This rejects a direct match to the comparator's striking ECB-like repeat statistic but does not rule out non-ECB encryption, compression, proprietary encoding, or plain structured content. Counts across 0/194/199-byte cuts and block sizes 8/16, top repeated values, input hashes, and bounded payload spans are reproducible with `python3 firmware/work/scripts/probe_roland_payload_block_repetition.py`; output is `firmware/work/roland-payload-block-repetition.json`. The method and comparison limitations are embedded in that evidence file.

TONE3000's current embedded A2-Lite engine has a Cortex-M7/Thumb-2/FPv5-optimized path (and a separate Cortex-A76 path). At 48-sample blocks it reports 4,059 cycles/sample on a 480 MHz Cortex-M7, about 41% of that core; its state consumes about 100 KiB, code 12.4 KiB, and the `.namb` capture 7,980 bytes. The GT-1 officially samples at 44.1 kHz, while this A2-Lite engine documents 48 kHz input and no resampling API. A compatible pipeline therefore needs model adaptation or 44.1↔48 kHz resampling; the NAM stage alone corresponds to about 194.8 million M7-equivalent cycles/second at 48 kHz, before conversion, remaining effects, and system workload. Since ESC2's ISA, clock, usable low-latency RAM, and spare cycles remain unknown, feasibility is **undetermined** and compatibility is not established.

The named application pools currently identified total 36 KiB of address range (`stack pool` 32 KiB plus `general pool` 4 KiB), which is smaller than the A2-Lite state estimate. This is only a lead for RAM mapping: these named regions may have narrow roles, other RAM and pools may exist, and the ranges are not evidence of free capacity. Do not treat this comparison as a feasibility verdict.

### Image layout and version comparison (verified locally)

All four images are 4 MiB and contain `ESC91.000` at `0x000000`, `BSSESC2:GT1Upd` at `0x002000`, and `BSSESC2:GT1Appli` at `0x040000`. The application header's `+0x30` stored-length candidates are v1.05 `0x11E058`, v1.07 `0x11E765`, v1.08 `0x11E7C5`, and v1.09 `0x11FAFA`; the updater's corresponding candidate remains `0x21567` in all four. These are structural observations; field semantics remain unproven.

The `GT1Upd` and `GT1Appli` headers at `0x2000` and `0x40000` share a 0x40-byte layout. In the four images, the updater `+0x30` word remains `0x21567`; it spans stored payload from `0x2040` through exclusive end `0x235A7`. The application `+0x30` candidates are v1.05 `0x11E058`, v1.07 `0x11E765`, v1.08 `0x11E7C5`, and v1.09 `0x11FAFA`; for v1.08/v1.09 they span to `0x15E805` / `0x15FB3A`. The next non-`0xFF` data after app padding begins at `0x1FC000`. The `+0x3C` word is `0x2A478` for the updater and app values are `0x2CAFD8`, `0x2CBA90`, `0x2CBB18`, and `0x2CD2B4` for v1.05, v1.07, v1.08, and v1.09, respectively; they are plausible expanded-size candidates. This strongly supports a stored-length field at `+0x30` and an expanded-length candidate at `+0x3C`, but no tested standard decoder yielded those output sizes. Common zlib/deflate, gzip, bzip2, LZMA/XZ, LZ4-frame/raw-block, Zstandard-frame, Brotli, and LZO1X probes failed on bounded payloads and selected suffixes; the raw-block LZ4/LZO tests use the `+0x3C` field as the expected output-size candidate. This still leaves proprietary formats and non-compression transformations open. The `+0x34` word matches a 32-bit additive byte sum over the stored payload in all eight block/version cases (two blocks × four versions): `sum(payload bytes) mod 2^32`. Other tested sums, XOR, CRC-16/CRC-32, CRC-32C, and Adler-32 do not match over the obvious alternate scopes. This strongly identifies `+0x34` as a weak payload integrity checksum field; it does not prove the updater verifies it or establish cryptographic authentication. Full computed values and hashed spans are recorded in `firmware/work/header-integrity-candidates.json`, generated by `python3 firmware/work/scripts/reproduce_header_integrity_candidates.py`. Header fields at `+0x28` and `+0x38` are both `0x60000000`, and `+0x2C` is `0x40`; their semantics are unknown. Exact offsets, hashes, padding, and tested codec results are reproducible with `python3 firmware/work/scripts/reproduce_container_layout.py` and `python3 firmware/work/scripts/reproduce_section_suffix_codec_probes.py`; results are recorded in `firmware/work/container-layout.json` and `firmware/work/section-suffix-codec-probes.json`.

**GT-1B cross-product checksum and ROMINFO check:** the official [GT-1B support page](https://www.boss.info/global/support/by_product/gt-1b/updates_drivers/) publishes v1.04, and BOSS's [Taiwan regional page](https://tw.boss.info/support/by_product/gt-1b/updates_drivers) lists v1.03 and v1.02; their Roland-hosted archives have been preserved under `firmware/work/reference/gt1b-comparator/`. Across all four GT-1 and three GT-1B packages, normalized `ROMINFO.TXT` content is exactly `0064,0507,4096` (decimal fields 64, 507, 4096); older archives include CRLF, while GT-1 v1.09 and GT-1B v1.04 omit the line ending. This supports the fields being shared updater metadata, but their meanings remain unknown. GT-1B v1.04 bytes `0x000000–0x001FFF` are identical to GT-1 v1.09, SHA-256 `70e91d0d1e6159007930eb5af0a90dc97038528ecb56af55943350a49e77573d`, so the initial bootstrap region is shared across these models. The `+0x30` bounded payload-length candidate and `+0x34` checksum relation also reproduce in GT-1B's two 0x40-byte-header blocks across v1.02/v1.03/v1.04, but the checksum convention differs: for GT-1, `+0x34 == sum(payload bytes) mod 2^32`; for GT-1B, `+0x34 == ~sum(payload bytes) mod 2^32` (equivalently, checksum field plus byte sum is `0xFFFFFFFF`). The relation holds for all 14 bounded spans (two blocks × seven images). This cross-product evidence strengthens the interpretation of `+0x34` as an additive integrity field with product-family-specific polarity, while still not proving the updater checks it. Package/image hashes, exact spans, raw ROMINFO bytes and line endings, and the full arithmetic are reproducible with `python3 firmware/work/scripts/reproduce_gt1b_comparator.py`; output is `firmware/work/gt1-gt1b-comparator-evidence.json`.

**Prior-study cross-check:** xintrea's 2024 [Russian-language GT-1 firmware study](https://webhamster.ru/mytetrashare/index/mtb0/17186974979qcubc1ew5) independently reports the `ESC91.000`, `BSSESC2:GT1Upd`, and `BSSESC2:GT1Appli` markers, and interprets the first two payloads as updater and application. Rechecking the preserved v1.08/v1.09 images confirms the marker offsets `0x000000`, `0x002000`, and `0x040000`, respectively. The same arithmetic reproduces the v1.08 end at `0x15E805`. We also confirm its reported v1.09 byte sequences at `0x0B8914` and `0x0BEBE4`; their looper-capacity interpretation remains unproven (see the looper analysis below). The local hashes are v1.08 `SHA-256 7219679a87e985316264544423c9940ccbcbadeb2df0b2f13711ae57194cb612` and v1.09 `SHA-256 412ebf5ffdc48554454c27df47f61428f046ea0a7d93f5c77b7f0302861abdbf`. Across the four images, 3,016,456 of 4,194,304 bytes fall into runs that are identical in all versions (312 maximal runs); the entire region `0x000000–0x00200F` is unchanged. Each adjacent-version pair has only 12–15 changed bytes outside `0x40000–0x1FC000`, the application partition candidate. **Release-note control check:** BOSS states that v1.09 changed the version number for management-related reasons and that product specifications were unaffected ([official update history](https://www.boss.info/us/support/by_product/gt-1/updates_drivers/076a30a8-a319-4891-94e4-ef0bb08451e5/)). Until that is resolved, cross-version byte diffs should be interpreted as positional evidence only. **Normalized periodic-record comparison:** as a targeted check for structured islands that raw same-offset comparison might miss, a second scan allows only the five byte values `0xFF`, `0xF7`, `0xFD`, `0xDF`, and `0xBF` as candidate markers. Those values appeared as periodic skipped bytes in the separate runtime-string projection; they are not known table delimiters. The scan looks for at least 12 nine-byte steps in which a candidate marker is followed by eight bytes that parse as two plausible little-endian float32 values, then compares exact concatenated eight-byte record payloads after omitting markers. It finds 23 exact projected-data matches for v1.05→v1.07 (14 at offset delta `-0x4DEC`, 9 at `+0x684`), none for v1.07→v1.08, and 7 for v1.08→v1.09 (all at `+0x1180`). Examples are v1.05 `0xD9764` ↔ v1.07 `0xD4978` (62 records), v1.05 `0xB2F3B` ↔ v1.07 `0xB35BF` (52 records), and v1.08 `0xD6FF2` ↔ v1.09 `0xD8172` (96 records). In every retained exact hit the separator-byte sequences also happen to be identical; removing them did not create a match whose marker sequence differed. This yields a few exact repeated islands within otherwise highly different payload bytes, with release-dependent offsets and gaps. It does not establish float use, record semantics, executable status, runtime relocation, or a single application-wide normalization transform; the selected marker set and float filters can produce false positives. Input hashes, candidate counts, marker sets, offsets, pair samples, and limitations are recorded in `firmware/work/periodic-float-chain-projection-evidence.json`, reproducible with `python3 firmware/work/scripts/reproduce_periodic_float_chain_projection.py`.

The file has high-entropy regions, but that does not establish compression or encryption. A gzip-looking byte sequence at `0x165E0` fails gzip decompression with “Unknown compression method” in both versions, so it is not a validated gzip stream. REA running Binwalk 3.1.0 reports four candidates in v1.09 and two in v1.08; detailed evidence is recorded below. The v1.09 candidate zlib byte ranges fail decompression, while its GPG-like ranges have not validated as OpenPGP signed content. LZ4, LZMA, and Zstandard libraries are available locally, but no valid stream or extracted app payload has yet been confirmed. Roland support describes the update `.BIN` as a proprietary format read by Roland/BOSS devices during updating; this supports treating it as a vendor container but does not establish encryption or cryptographic authentication ([Roland support](https://support.roland.com/hc/en-us/articles/23178648391195-Do-I-need-to-open-the-BIN-file-when-updating-the-System-Program)). At application offset `0x40030`, v1.09 has the little-endian value `0x0011FAFA`; at `0x40034`, `0x0886AB09` (the verified additive payload checksum); and at `0x4003C`, `0x002CD2B4`. The `+0x30` and `+0x3C` semantics remain candidate stored/expanded lengths, respectively.

## 2. Processor architecture and Ghidra

### Verified board identification

The GT-1 service-note block diagram identifies IC21 as `ESC2`; the main chip marking `MB8AA4181 (ESC2)` is reported by the third-party board study. The block diagram labels IC2 as `128Mbit SDRAM (WORK)` and IC3 as `64Mbit SDRAM (ERAM)`, for **24 MiB nominal external SDRAM total**. It labels IC10 as the AF A/D converter, X1 as a 48 MHz source, and a `CKCPU` net. This is evidence for a 48 MHz clock source/net on the board, but not enough to establish the ESC2 core's operating frequency, clock multiplication, or cycles available to software. The diagram shows ESC2 connected to external memory, audio conversion, and control circuitry. See the [GT-1 service-note block diagram](https://www.manualslib.com/manual/2485086/Boss-Gt-1.html?page=12) (a third-party mirror of Roland's service notes; searchable diagram labels include memory capacities and X1/CKCPU clock annotations).

A board-level community lead now gives direct visual evidence for one memory device: the March 2025 [Dhvan repair teardown](https://dhvan-assistenciatecnica.blogspot.com/2025/03/pedaleira-boss-gt-1.html) labels its images as the GT-1 top/control board and lower/main board. In its top-board photo `IMG_3186.JPEG` (locally preserved at `firmware/work/reference/gt1-board-photos/IMG_3186.JPEG`, SHA-256 `be01568125d2893a19c20de3a2636167f48b848b6c6f5c8d1f12ce7fdffc6d73`), the IC2 marking is visually readable as ESMT `M12L128168A-6T`; the [ESMT datasheet](https://www.esmt.com.tw/upload/pdf/ESMT/datasheets/M12L128168A%282L%29%20%28Automotive%20grade%29.pdf) identifies the family as 128 Mbit SDRAM (4 × 2M × 16). Its capacity matches the service-note WORK RAM capacity, but the photographed board's IC2 has not been mapped to the service schematic's IC2/WORK label. The teardown's lower/main-board photo (`IMG_3210.JPEG`, SHA-256 `3d8adaf338143488c62d19761c34862aec34d20affd09d9698b9493f95f08c02`) shows the main-board assembly marking `GT-1 PNB MAIN BOARD ASSY 5100051442`; its central IC1 marking is too faint to identify reliably in this image. These photographs do not visually establish the `MB8AA4181` marking, the other ERAM chip, debug pads, or a pinout. The blog also describes a GT-1 repair for failed signal processing, so it is a repair/teardown lead rather than a reverse-engineering or ISA report.

The GT-1 public product/service documents inspected do not disclose the ESC2 ISA, core count, FPU/DSP features, bus width, or **core operating clock rate**. Roland's own 2011 press release describes the ESC2 chip used in the BOSS RC-3/RC-30 as its “proprietary ESC2 DSP chip” ([Roland press release](https://www.roland.com/us/company/press_releases/2011/1283/)). This is evidence that Roland treats ESC2 as proprietary DSP silicon, but it does not state the instruction set or prove that every ESC2 generation/product has the same implementation. `MB8AA4181` appears to be a BOSS/Roland-specific part; searches did not locate an authoritative public Fujitsu architecture manual or instruction-set reference. A related-product schematic provides a materially stronger lead: Roland AD-10 service notes identify IC20 as ESC2 in the block diagram and IC20 as `MB8AA4181(ESC2)` in the digital circuit schematic; the block diagram groups debug/trace net names `TRST/TCK, SWCLK/SMS, SWDIO/TDI/TDO, SWV` with trace nets `TRCD0-3/DRCCKO` (printed pp. 10 and 25). Arm documentation describes SWV/SWO as Serial Wire Viewer/Output trace functionality for Cortex-M processors ([Arm Cortex-M debug/trace overview](https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/beginner-guide-on-interrupt-latency-and-interrupt-latency-of-the-arm-cortex-m-processors), [Arm trace overview](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/Understanding%20Trace.pdf)). This makes an ARM Cortex-M-style debug/trace interface a credible, moderate-confidence ISA-family hypothesis for the MB8AA4181 implementation, despite the proprietary-DSP branding. It is not a confirmed CPU identification: the labels are multiplexed alternatives on another product's schematic and do not prove a particular Cortex-M core, enabled debug features, or that the GT-1 chip has identical configuration. The GT-100 service notes also identify `MB8AA4181(ESC2)` and show a connector labeled `JTAG for ESC2`; JTAG by itself is architecture-neutral and adds no ISA evidence. GT-1 service notes identify IC21 as ESC2 but do not expose this debug/trace labeling in their searchable block diagram; the MB8AA4181 marking on GT-1 itself remains community-reported. Separately, bounded Thumb/Thumb-2 disassembly is now supported in both the GT-1 initial `ESC91.000` region and the FA-08 `ESC90.000` region. This shows ARM Thumb code in those image regions, but cannot yet be attributed to the MB8AA4181 core or to either product's main application firmware.

### Ghidra support

Ghidra's official processor-language definitions include ARM Cortex/Thumb languages, including M-profile variants ([Ghidra ARM language definitions](https://github.com/NationalSecurityAgency/ghidra/blob/Ghidra_12.2_build/Ghidra/Processors/ARM/data/languages/ARM.ldefs)). The official Ghidra 12.2 distribution was installed locally and its checksum verified against the NSA release page. For GT-1 v1.09, we imported only the first 8 KiB (`file 0x000000–0x001FFF`) using built-in `ARM:LE:32:Cortex`, base `0x00FFFFD0`, and Thumb context. A headless Ghidra script seeded at file offsets `0x2F0` and `0xB14` reports 755 instruction records in that range; the `0x2F0` excerpt begins `ldr.w sp, [0x010002d0]` / `bl 0x01000bb0`, and the reset trampoline at `0xB14` begins `ldr r0, [0x01000afc]` / `bx r0`. For FA-08 `fantom_e_up.bin`, a separate import of only its first 8 KiB using the same language and candidate base decodes the entry at file `0x2F4` and init-table loop at `0xA18`; the loop's two literal bounds resolve to plausible nearby table data under the candidate mapping. Capstone and Ghidra agree on these bounded blocks, and FA's 24-byte loop at `0xA18` exactly matches GT-1's loop at `0xBE0`. These checks validate Ghidra's ARM Thumb decoder for those snippets, not the chip identity or application ISA. The GT-1 count includes reachable decoding around mixed code/data and is not a count of verified functions; some words/padding are not valid instructions. None of this identifies the ISA of `GT1Upd` or `GT1Appli`, or proves that either bootstrap executes on an MB8AA4181/ESC2. No custom processor module is needed for the confirmed Thumb snippets. The exact ESC2 core variant, optional coprocessor/FPU features, endianness, and application payload ISA remain unknown; a SLEIGH module should be considered only if later evidence identifies an unsupported app ISA.

The bytes around file offset `0x0002F0` decode coherently as Thumb/Thumb-2 in Capstone and, for this bounded block only, in Ghidra. A 2024 reverse-engineering forum thread independently proposes load base `0x00FFFFD0` for the first image block, with a 0x30-byte header before the vector table ([thread, address-map discussion](https://www.linux.org.ru/forum/talks/17651382), comments at 627–629 and 651–665). This model is consistent with the local binaries: file offset `0x30` maps to runtime `0x01000000`; the reset vector at `0x34` (`0x01000AE5`) maps, after clearing the Thumb bit, to file offset `0x0B14`; code there loads literal `0x010002C1` and branches to startup at file offset `0x2F0`. At `0x2F0`, `ldr.w sp,[pc,#0xc]` loads `0x01028000`, `bl` reaches runtime `0x01000BB0` (file offset `0x0BE0`), and the later `ldr`/`bx` uses literal `0x010009F1` to enter code at file offset `0x0A20`. These vector, literal, and relative-branch anchors form a coherent startup chain and support `runtime = 0x00FFFFD0 + file_offset` for the initial `ESC91.000` block. This corrects the earlier `0x01000000 + file_offset` hypothesis, which was offset by the 0x30-byte header. The mapping does not establish the load address or ISA of the later `GT1Upd` payload at `0x2000` or `GT1Appli` at `0x40000`, nor prove that `ESC91.000` executes on the GT-1's MB8AA4181/ESC2 audio processor. Exact anchors and both-version comparison are in `firmware/work/updater-address-map-hypothesis.json`; regenerate with `python3 firmware/work/scripts/reproduce_esc91_map.py` (Capstone required). The scoped Ghidra project/report and reproduction script are `firmware/work/ghidra-projects/GT1_ESC91.gpr`, `firmware/work/ghidra-esc91-thumb-analysis.txt`, `tools/ghidra_scripts/GT1ThumbBlock.java`, and `firmware/work/scripts/run_ghidra_esc91.sh`. This is not an application disassembly.
**Cortex-M-style vector-table cross-check:** parsing the 176 words at file `0x30` in GT-1 v1.08/v1.09 and KATANA v2.01/v4.00 gives an initial stack-pointer word, 15 core exception slots, and 160 further interrupt slots. Arm's Cortex-M startup documentation describes the same table organization: initial stack pointer, reset handler, core exceptions, then external interrupts ([Arm startup-file explanation](https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/decoding-the-startup-file-for-arm-cortex-m4)). In all four images the five zero entries are vector indices 7–10 and 13; all 170 nonzero handler entries have the Thumb bit set and map into the first 8 KiB under the candidate address map. All 160 external interrupt entries share one default handler (`0x01000AFB` in GT-1, `0x01000A33` in KATANA). Target decoding adds behavioral structure: the reset vector in both products enters a two-instruction `ldr`/`bx` trampoline; GT-1's NMI/fault/SVC/DebugMon/PendSV slots each land on their own 16-bit self-branch stub, and vector 15 (the Cortex-M SysTick slot) points to a distinct Thumb routine at file `0x604`. That routine reads a word through literal `0x01010000`, increments it, and writes the result through literal `0x40005000`; the destination's hardware meaning is unknown. KATANA's corresponding core exception slots, including vector 15, land on self-branch stubs. The GT-1 v1.08/v1.09 first 8 KiB hashes are identical, as are the KATANA v2.01/v4.00 vector words. This exact slot pattern, together with target code and independently decoded startup control flow, is substantially stronger evidence for Cortex-M-style code in `ESC91.000` than isolated plausible instructions. It still identifies a code format rather than the physical CPU: the bootstrap could be a separate boot component, and the data does not prove execution on MB8AA4181/ESC2 or identify the application ISA. Reproduce the parse, target disassembly, and per-image hashes with `python3 firmware/work/scripts/reproduce_cortex_vector_table_evidence.py`; full vector words, counts, invalid-entry scan, target samples, and limitations are in `firmware/work/cortex-vector-table-evidence.json`.

**Katana ESC91 cross-version check:** official original-series KATANA v2.01 and v4.00 images provide an independent test of the same candidate map. In both 4 MiB images, the vector table begins at file `0x30`, the initial stack word is `0x01011238`, and reset vector `0x01000A1D` (Thumb bit set) points to file offset `0xA4C` under `runtime = 0x00FFFFD0 + file_offset`. Thumb-M decoding there yields `ldr r0, [pc, #0x14]` / `bx r0`; its literal at `0xA64` is `0x010002C1`, which maps to startup file offset `0x2F0`. At `0x2F0`, Capstone decodes `ldr.w sp, [pc, #0xc]` and a branch-with-link; the target differs between v2.01/v4.00, `0x0B30`/`0x0B24`. Their first 8 KiB blocks have 7,884 of 8,192 same-offset bytes in common; the longest identical run is `0xC50–0x1FFF` (5,040 bytes). This corroborates Thumb code and the candidate map in the Katana `ESC91.000` block only. It does not show that the main `AP068` updater/application payload is ARM or that GT-1's audio core executes this block. Reproduce with `python3 firmware/work/scripts/probe_katana_esc91_map.py`; full vectors and disassembly are in `firmware/work/katana-esc91-map-probe.json`. Same-offset firmware version comparison (including bounded payloads and hashes) is in `firmware/work/katana-version-comparison-evidence.json`, generated by `python3 firmware/work/scripts/reproduce_katana_version_comparison.py`.

A recovered ARM Compiler runtime diagnostic gives a separate toolchain clue. A modulo-9 nonprintable-byte projection recovers the exact normalized `SIGPVFN: Pure virtual fn called` phrase in all four GT-1 app payloads, GT-1B v1.04, GT-100 v2.12, and KATANA v2.01/v4.00; exact offsets, skipped-byte values, phases, raw-span hashes, and input hashes are recorded in `firmware/work/runtime-string-version-evidence.json`. Arm’s [Compiler for Embedded Arm C and C++ Libraries and Floating-Point Support User Guide](https://documentation-service.arm.com/static/6526c2dd9e189a266cef7fb0) identifies this as ARM Compiler C++ runtime behavior. This makes ARM Compiler runtime/library content plausible across these app objects. It still does not prove the executable ISA, handler reachability, or that the matching payloads execute on the MB8AA4181; the GT-1 application bytes remain undecoded.

The string/record cadence does not appear as a globally distinctive modulo-9 byte lane. Across GT-1 v1.05/v1.07/v1.08/v1.09, each of the nine application-payload lanes has entropy between 7.679 and 7.700 bits/byte; GT-100 v2.12 ranges from 7.700 to 7.707. No one lane is consistently low-entropy or restricted in byte values. This weakens a simple whole-payload “eight data bytes plus one special marker lane” interpretation while leaving local 9-byte records and marker-skipping string encodings viable. Reproduce per-lane frequencies and image/payload hashes with `python3 firmware/work/scripts/probe_payload_mod9_lane_entropy.py`; the output is `firmware/work/payload-mod9-lane-entropy.json`.

## Prior GT-1 reverse-engineering leads

### Fx FloorBoard source: static SysEx and parameter reference

The public [GT-1 Fx FloorBoard project](https://sourceforge.net/projects/fxfloorboard/files/GT-1FxFloorBoard/) is a reusable source of GT-1 control-protocol evidence, not firmware or CPU reverse engineering. Its 2026-04-05 source archive is preserved at `firmware/work/reference/gt-1_fxfb_source_code_20260405.zip` (SHA-256 `bacc2c0f4c37bfa19e3a85004f2b60021d76cec520618fdf90edba22eb2e6d55`); extracted files are under `firmware/work/reference/gt-1/`. The archive includes source, a `midi.xml` parameter map, patch examples, and protocol handling code. The individual `midi.xml`, `MidiTable.cpp`, and `SysxIO.cpp` hashes are respectively `c802b38b73d88ff92f6c8bf3863afe01c9faa6eac6fe5e26be28ca4f70033547`, `ebb939be926d3fedca09fa9044273dad8c318a105036ed938ca0ce58765e95cb`, and `a034d02133037437412d336d6c3c408130a43ec71c755cb0964b09d38e384e9b`.

Static source inspection finds the GT-1 SysEx framing and parameter model: `midi.xml` lists Roland manufacturer ID `0x41`, GT-1 model bytes `00 00 60`, DT1 command IDs `0x11`/`0x12`, and address regions for temporary bulk/individual buffers. `globalVariables.h` sets the address and checksum start offsets to byte 7 (zero-based), identifies data at byte 11, and includes a system-data read request. `MidiTable.cpp` constructs request/write messages and implements the Roland checksum as the two's complement of the sum modulo `0x80`; patch addresses are mapped across user and preset banks. The editor's patch structure map names amp/preamp and effect parameters, while its source warns in places that some fields derive from GT-100/GT-1000 conversion or inherited mappings. These are reverse-engineered/editor-maintained protocol tables and should be treated as reported community evidence until independently validated against captured GT-1 traffic or official Roland documentation. The exact local file hashes and key static findings can be regenerated with `python3 firmware/work/scripts/reproduce_fxfloorboard_evidence.py`; output is `firmware/work/fxfloorboard-source-evidence.json`.

The included `default.tsl` contains one GT-1-labeled patch with values such as `preamp_a_type=4`, `preamp_a_gain=80`, and `fx1_sub_od_ds_type=12`. The archived `new_default.syx` has 19 fixed 141-byte SysEx messages; all 19 checksums validate under the editor's checksum function. Their address fields cover `0x60000000–0x60001000`, followed by two additional messages at `0x60000D00` and `0x60000E00`; the first message's model byte is `0x2F` while the remaining 18 use `0x60`, so the first header remains an unexplained variant. These samples provide reproducible patch/control traffic and demonstrate that amp selection/gain are patch-level settings. They do not map those settings to amp-model code or weights in `GT1ROM.BIN`; the updater's payload is still not decoded. The script records all message offsets, addresses, lengths, checksums, and sample patch fields in `firmware/work/fxfloorboard-source-evidence.json`.

This is useful for safe, offline work on saved patch/SysEx files, parameter-map comparison, and later controlled read-only capture of normal editor traffic. It does **not** expose firmware memory, establish an undocumented command that can load code, or identify an audio processing insertion point. FxFloorBoard writes patch/system data when used interactively; no device was connected or commands sent in this investigation.

**Amp-block integration lead:** the official GT-1 product page lists a dedicated PREAMP button and documents 44.1 kHz sampling ([BOSS GT-1 product/specifications](https://www.boss.info/us/products/gt-1/downloads/?lang=en-US)); BOSS also lists a [GT-1 Parameter Guide / Sound List](https://www.boss.info/global/support/by_product/gt-1/owners_manuals/). The official guide (printed p. 3) shows PREAMP as a distinct node in the editable effect chain and explicitly documents selecting an effect and moving it with the knob. Its sample chain places PREAMP among OD/DS, noise suppression, delay, and other blocks. It (printed p. 12) lists preamp types, and (printed p. 18) describes the PREAMP controller function as switching the combined PREAMP/SPEAKER block on/off. These primary docs establish a user-visible, reorderable preamp/speaker effect node; they do not prove its internal implementation, whether it contains separable amp and cabinet stages, or whether its processing can be replaced without altering adjacent stages.

The official parameter guide describes PREAMP as using COSM technology to simulate preamp characteristics, speaker sizes, and cabinet shapes; it lists TYPE, GAIN, LEVEL, BASS, MIDDLE, TREBLE, PRESENCE, BRIGHT, and SP.TYPE controls (printed p. 11–12). It separately documents OD/DS and PREAMP effect blocks and explicitly says the PREAMP controller switches the combined PREAMP/SPEAKER on/off (printed p. 18). This verifies the product-level amp/cabinet controls and user-visible block boundary, but not that the amp and cabinet are internally separable or that the signal-processing stage can be replaced while retaining the other blocks.

Fx FloorBoard's patch examples expose preamp A/B state, type, gain, EQ, level, speaker/mic, and custom-preamp fields; its source maps these fields into byte positions in its patch template, and stores an example 20-element effect-chain ordering. We extracted the relevant fields and template positions with `python3 firmware/work/scripts/reproduce_amp_control_lead.py`; evidence, source hashes, and limitations are in `firmware/work/amp-control-lead-evidence.json`. These remain community-editor patch/control-plane leads only. The `temp.mid()` and `GT100_default_replace()` indices are template byte offsets, **not** verified GT-1 SysEx addresses or firmware locations; the latter function name itself reflects a GT-100-derived conversion path. The chain example is not enough to establish firmware runtime order. Combined with the official guide it suggests the PREAMP/SPEAKER chain node as the strongest user-visible conceptual replacement boundary to investigate, but it says nothing about the DSP call graph or whether firmware exposes a replaceable stage.

### Direct firmware work: 2024 GT-1 looper study

A public 2024 [GT-1 firmware study](https://webhamster.ru/mytetrashare/index/mtb0/17186974979qcubc1ew5) by xintrea is the most directly reusable work found. It obtained official v1.08 and v1.09 images, compared their 4 MiB layouts, identified the `BSSESC2:GT1Upd` and `BSSESC2:GT1Appli` markers, and independently noted the main app's changed region ending near `0x15FB39` followed by `0xFF` padding. These observations overlap our local binary analysis and provide useful provenance/context. The author did not decode the application, identify the CPU ISA, or produce modified firmware. Its byte dump at file offset `0x2F0` also matches the updater bytes in our local images, but that is a narrow corroboration rather than independent evidence of the app ISA.

The study's looper search reports byte sequences `40 99 80` at v1.09 file offset `0x0B8914` and `80 99 40` at `0x0BEBE4`; our full-image search across all four preserved releases finds those exact values twice in v1.05 (`80 99 40` at `0x0A7CA6` and `0x153A5A`), twice in v1.07 (`40 99 80` at `0x0491E1` and `0x13082A`), nowhere in v1.08, and once each at the reported v1.09 offsets. Every occurrence is inside the bounded application payload, but only v1.09 places them at xintrea's offsets. Each byte order decodes to `0x409980`, and `3 * 44,100 * 32 = 4,233,600 = 0x409980`. The numeric match is exact but is less specific than it first appeared because the same triplet values occur at other application offsets in earlier releases. In v1.09, the `0x0BEBE4` little-endian value sits among regularly spaced 24-bit values around `0x409900`–`0x409AA0` (e.g. `0x409980`, `0x409984`, `0x409990`). A bounded 8+1-record float-pair probe over 288 bytes around `0x0BEBE4` does not support a local float interpretation: across all nine phases its best phase has 16/31 pairs with both values finite and within ±100, while 256 deterministic byte-shuffle nulls have a median best-phase fraction of 0.469 and beat or tie the observed score 65 times. This null is only a rough negative control, but the observation is not unusually structured by this test. Both v1.09 candidate windows lie in highly version-changing data: 507 of 512 bytes differ in `0x0B8800–0x0B89FF`, and 383 of 384 differ in `0x0BEB00–0x0BEC7F`. ### Community container/code-region hypotheses

A Linux.org.ru discussion about the same dump proposed that the `GT1Upd` object contains compressed data, an internal table near `0x1BBB0`, and code-like material around `0x20400`; it also flagged the `0x235A8` area as the start of erased fill and suggested ARM Thumb decoding for the first block. These are community hypotheses, not a format decode. Local evidence verifies that the length word at `0x2030` yields a payload from `0x2040` ending at exclusive offset `0x235A7`, followed by `0xFF` fill, while the advertised expanded-length candidate at `0x203C` is `0x2A478`. The app block has the same 0x40-byte header pattern and stored/expanded length fields. Standard gzip, zlib/raw-deflate, bzip2, LZMA, LZ4 frame, and Zstandard decoders fail on the exact bounded payloads; 7-Zip’s archive probe also does not recognize either span as an archive (including LHA/LZH). The proposed table/code boundaries `0x1BBB0` and `0x20400` remain unclassified; Capstone’s ARM decoder emits short, incoherent snippets at `0x20400`, which is insufficient to call that region ARM code. The community discussion also notes matching loader content across versions; locally, exactly 12 bytes differ in the full `0x2000–0x40000` update block, all within its changing header at `0x2010–0x201F`.

The same thread adds hardware/layout leads: its author reports an ESMT `M12L64164A` SDRAM marking, and a commenter estimates effect-parameter data begins around `0x1FE000`. The article's retrievable embedded images are firmware hex-comparison screenshots; they do not provide a readable chip-photo corroboration for the memory marking. ESMT's [official datasheet](https://www.esmt.com.tw/upload/pdf/ESMT/datasheets/M12L64164A%282C%29.pdf) confirms that this part is 64 Mbit (8 MiB), organized as 4 × 1M × 16. That capacity matches the service diagram's 64 Mbit ERAM, but the community report does not establish its IC reference or board revision. Separately, the March 2025 [Dhvan repair teardown](https://dhvan-assistenciatecnica.blogspot.com/2025/03/pedaleira-boss-gt-1.html) gives a readable photo of top/control-board IC2 marked ESMT `M12L128168A-6T` (128 Mbit); this is consistent with the service diagram's 128 Mbit WORK RAM. The same article's lower-board photo shows assembly marking `5100051442`, agreeing with the GT-1 service-note part list, but it does not resolve the ESC2 chip marking. The service diagram's two capacities total 24 MiB nominal; neither source establishes available/free memory or a software-visible address map. In our official v1.09 image, the first non-`0xFF` byte after the app’s erased gap is at `0x1FC000`; `0x1FE000` is therefore not the beginning of all post-app data, though it may still mark a subregion. The same commenter places a sparse tail beginning around `0x331758`; that address is indeed `0xFF` in the local image. Preserve these offsets as targets for structural comparison, not section labels.

## 3. Security and integrity mechanisms

**Verified updater behavior:** BOSS says enter updater mode by holding EXIT while powering on, connect USB, copy both unrenamed files to the mounted `BOSS_GT-1` drive, safely eject/disconnect, then press ENTER at “Push [ENTER] to start.” BOSS warns not to interrupt power and says service may be required after an interrupted update. Static headers identify a simple additive checksum over each stored payload, but this documented flow does not reveal whether or when the updater validates it or whether it uses additional authentication.

**Factory reset is not firmware recovery:** Roland's [GT-1 factory-reset instructions](https://support.roland.com/hc/en-us/articles/215222643-GT-1-Factory-Reset-Initialization) state that reset clears user/system settings and patches while retaining the last installed system program version. The page's wording “roll back” could be misread; its example makes clear that a factory reset does not downgrade firmware or recover an interrupted update. No documented consumer firmware rollback or recovery path has been found.

The GT-1 service notes add a documented **user-data backup** path: send two SysEx requests from a MIDI sequencer, record the returned system settings and U01–U99 patch bulk data, and save the recording; the manual estimates 40–50 seconds for transfer (printed p. 15). This is not a firmware dump or firmware rollback procedure. The service manual's update procedure enters `GT-1 Updater` by holding EXIT while connecting a dummy plug to INPUT, then exposes a `BOSS_GT-1` USB drive for copying `GT-1ROM.BIN` and `ROMINFO.TXT`; its service updater is described as obtained through Service Net (printed p. 16). The current consumer instructions describe the same USB-copy/ENTER-start flow. Neither document describes a second-stage recovery mode or recovery after failed/corrupt firmware; BOSS's stated service requirement after an interrupted update remains the only documented failure recovery.

**Verified image integrity field:** At each GT-1 updater/application block header, the little-endian word at `+0x34` equals the sum of stored payload bytes (starting at `+0x40`, length from `+0x30`) modulo `2^32` in all eight version/block cases. This is a weak additive checksum, not a cryptographic signature.

| Firmware | Updater payload checksum (`+0x2034`) | Application payload checksum (`+0x40034`) |
|---|---:|---:|
| v1.05 | `0x01000EBA` | `0x08774CDF` |
| v1.07 | `0x01000EBA` | `0x0874473C` |
| v1.08 | `0x01000EBA` | `0x0878B479` |
| v1.09 | `0x01000EBA` | `0x0886AB09` |

The same direct-sum relation matches both GT-100 v2.12 blocks: updater `0x01035B7B` over `0x2040–0x2379C`, and application `0x0938DC1E` over `0x40040–0x17689B`. The GT-100 image SHA-256 is `0c44ab01ac310927bf8dcc95f4ab5fcc487ed106dfcc6fc067832a35a4e32d34`. GT-1B v1.02/v1.03/v1.04 also matches the bounded byte sum in both blocks, but stores its one's complement at `+0x34`; across the six GT-1B spans, `checksum + byte_sum == 0xFFFFFFFF`. Thus the header carries an additive integrity relation across these three product families, with GT-1B using the inverse polarity. This does not prove the GT-1 updater enforces it. The GT-1/GT-100 calculation, input hashes, and span hashes are in `firmware/work/header-integrity-candidates.json`; GT-1B cross-product evidence is in `firmware/work/gt1-gt1b-comparator-evidence.json`. `ROMINFO.TXT` remains `0064,0507,4096` across both GT-1 and GT-1B, with decimal fields 64, 507, and 4096; their meanings are not decoded. Neither the image field nor BOSS's documented update process proves the checksum is checked before applying the image.

No verified evidence of encryption, a cryptographic signature, cryptographic hash, anti-rollback enforcement, secure boot, or recovery partition has been found. A simple additive payload checksum is verified in the image headers; whether the updater enforces it is unknown. High entropy alone would not prove encryption. The updater is accessible from a physical button sequence, but the available documentation does not establish a boot ROM, alternate recovery path, or ability to recover from a corrupted main image. The documented failure mode is service intervention.

## 4. Audio-processing architecture hypotheses

The official product specification lists 44.1 kHz sampling, 24-bit AD and DA conversion, BOSS AF conversion method, and a broad set of effects and amp tones. The GT-1 service-note block diagram labels an AF A/D block at IC10, ESC2 at IC21, an AD/DA block at IC5, SFI at IC9, 128 Mbit WORK SDRAM at IC2, and 64 Mbit ERAM at IC3. At block-diagram level this supports a converter–ESC2–converter processing topology with external work/effect memory, alongside input/output buffering and a 48 MHz CKCPU source/net. It does not establish the exact digital audio link, bus width, serial format, converter sample framing, memory bandwidth, or detailed scheduling/effect partition. The service-note circuit pages are schematics, but their text extraction alone does not expose enough net-level detail to reconstruct those interfaces.

**Hypothesis:** the ESC2 likely executes control and/or audio processing using external memory and communicates with separate converter devices. The block diagram's IC labels support that broad role, but it is not established whether all audio algorithms execute on ESC2, whether it has hardware MAC/FPU acceleration, whether there is a second DSP, or where in the pipeline amp modeling occurs. The schematic-level converter interfaces and IC21 memory/control buses should be visually reconstructed before proposing a tap point; the available searchable text does not provide a reliable net list.

A reasonable future integration point, if processor and timing permit, is replacing the amp/preamp model stage while leaving the surrounding effects and patch control intact. But the firmware's block scheduling, internal sample representation, effect ordering, and latency budget are not publicly established. Any 44.1-to-48 kHz conversion for the embedded NAM engine would also add work and likely buffering/latency.

## 5. NAM A2-Lite feasibility assessment

The upstream [TONE3000 embedded repository](https://github.com/tone-3000/embedded) release 2.0.0 is pinned locally at commit `b84b60c652cb386ea341be50b8c665ae8a489cff` in `firmware/work/reference/tone-3000-embedded/`. SHA-256 values for the README, manifest, engine and benchmark sources, reader, and `.namb` are recorded in `firmware/work/nam-source-evidence.json`, regenerated by `python3 firmware/work/scripts/reproduce_nam_source_evidence.py`. A2-Lite has 23 layers, float32 weights (1,871 values), and a fixed 48 kHz sample rate. The repository supplies target-specific optimized implementations for Cortex-M7/Thumb-2/FPv5 and Cortex-A76/AArch64. The M7 source selects its assembly kernels only when GCC reports ARMv7E-M, FMA, and Thumb-2; those kernels use `VMAXNM`, which the upstream README says is absent on Cortex-M4F FPv4. The same M7 engine source also contains C tile kernels selected when `NAM_M7_ASM=0`; upstream says these give the same output more slowly and recommends them for M4F or any core without FPv5. Thus the NAM math is not inherently limited to Thumb-2, but the portable path still needs a suitable C compiler/runtime and scalar floating-point support. **The 4,059-cycle/sample block-48 figure is strongly indicated to measure the optimized M7 path:** the Daisy Seed benchmark defaults to 48-frame blocks and the base M7 engine, while the documented M7 flags satisfy the source's assembly-selection condition and the board Makefile does not disable it. The exact preprocessor output cannot be confirmed because the upstream source snapshot does not include that benchmark's compile log or object file. No C-fallback cycle figure is published, so do not apply 4,059 cycles/sample to that fallback. These target/build source hashes and limits are recorded in `firmware/work/nam-source-evidence.json`. The repository reports:

| Resource | A2-Lite figure published by upstream |
|---|---:|
| Processing | 4,059 cycles/sample on Cortex-M7, block 48; 4,403 cycles/sample with the M7 16-frame tuning |
| Runtime load | 41% of a 480 MHz Cortex-M7 at 48 kHz |
| Hot structs (weights + engine instance; 7.3 KiB + 1.9 KiB) | 9.2 KiB at max block 48 |
| State/ring buffers | 100 KiB at max block 48; 109 KiB at default max block 64 |
| Engine code | 12.4 KiB |
| `.namb` capture | 7,980 bytes |
| Model weights | 1,871 float32 values (7,484 bytes, included in runtime storage) |

A2-Lite is documented for 48 kHz. The upstream M7 block-48 result therefore yields the meaningful baseline of 4,059 × 48,000 = **194.832 million cycles/second** for the NAM stage. The M7 16-frame tuning is slower at 4,403 cycles/sample, or **211.344 million cycles/second** at 48 kHz; upstream also notes callback overhead occurs three times as often at 16 than at 48 frames. GT-1's callback block size is unknown. These are comparison baselines only: ESC2's core clock and instruction throughput are unknown, and an ESC2 build would not automatically use the M7 assembly. The service diagram's 48 MHz `CKCPU` clock source/net does not establish a 48 MHz core. Under the explicitly hypothetical condition that the ESC2 core runs at 48 MHz, each 48-frame/1 ms NAM callback has a total single-core budget of 48,000 cycles. The upstream M7 reference cost is 194,832 cycles for that callback, or 4.059 times the entire hypothetical budget (405.9% utilization), before resampling or other effects. A sensitivity calculation shows that even if ESC2 achieved one-quarter of the M7 reference's cycles/sample (four times fewer cycles), NAM alone would still require 101.5% of a hypothetical 48 MHz core. These are conditional arithmetic screens, not GT-1 measurements or predictions: the actual ESC2 core clock, architecture-specific implementation cost, and workload remain unknown. If its core runs substantially faster than 48 MHz or a native optimized implementation uses far fewer cycles than the M7 reference, the result could differ. The upstream API accepts frame counts and float buffers, and sets `NAM_A2LITE_SAMPLE_RATE` to 48000; its integration examples use mono float32 at 48 kHz. After initialization or reset, the header requires 6,347 silence samples to prewarm the recurrent state before normal processing. At 48 kHz this is 132.23 ms of sample history, or 133 calls at a 48-frame maximum block (the last call contains 11 frames). This is a startup/model-switch constraint separate from steady-state inference; an uninterrupted switch needs a prewarmed second instance/state or another transition strategy, which carries additional temporary memory and compute. The M7-equivalent arithmetic is about 25.76 million cycles (53.67 ms at 480 MHz), not an ESC2 measurement. No 44.1 kHz mode or resampler is documented. GT-1's official 44.1 kHz rate must therefore be reconciled by adapting/retraining the model or by inserting conversion. The rational 44.1→48 kHz ratio is 160/147: every 147 GT-1-rate input samples corresponds to 160 NAM-rate samples (3.333 ms). The inverse conversion is also needed if the following GT-1 processing remains at 44.1 kHz. The 48 kHz A2-Lite work for those 160 output samples is 649,440 M7-equivalent cycles, excluding both resampling filters, buffering, and existing firmware work. A direct call at 44.1 kHz would be outside the documented engine rate and its expected model time/frequency interpretation. None of these comparisons establishes feasibility.

The cycle, resampling, prewarm, and throughput sensitivity arithmetic is reproducible with `python3 firmware/work/scripts/reproduce_nam_feasibility_estimate.py`; JSON is `firmware/work/nam-feasibility-estimate.json`. A 48-frame NAM callback costs 194,832 cycles at the upstream M7 result and has a 1.00 ms deadline at 48 kHz. Under a hypothetical 48 MHz ESC2 core, that deadline provides 48,000 cycles; even an implementation four times more cycle-efficient than the M7 reference would need 101.5% of the entire core budget for NAM alone. A 16-frame tuned callback costs 70,448 cycles at the upstream result, has a 0.333 ms deadline, and occurs three times as often. A 147→160 resampling interval takes 3.333 ms; the NAM work in that interval is 649,440 cycles at the M7-equivalent result, not including conversion filters. The required 6,347-sample prewarm spans 132.23 ms and 133 48-frame calls; multiplying by the M7 average gives 25,762,473 reference cycles (53.67 ms at 480 MHz), not a dedicated bulk-prewarm benchmark. These budgets explain timing constraints but are not GT-1 measurements. The old 44.1 kHz multiplication is retained in the JSON only as an explicitly unsupported counterfactual. The 48 MHz comparison is conditional: GT-1 service notes show a `CKCPU` clock source/net at 48 MHz, not the ESC2 core's actual operating clock. The factors are sensitivity illustrations, not ESC2 performance predictions.

The benchmark memory layout is also material: upstream places the 9.2 KiB weights/instance structures in M7 DTCM, the 100 KiB ring-buffer state in AXI SRAM (or DTCM if it fits), and the 12.4 KiB engine code in ITCM or cached flash. The A2-Lite state header declares float ring-buffer arrays totaling 102,468 bytes (100.07 KiB) at a 48-frame maximum; this arithmetic is reproducible from the pinned header. The GT-1 service notes document external WORK/ERAM capacities but do not identify ESC2 on-chip SRAM/cache sizes or show equivalent low-latency memory regions. Its 24 MiB nominal external SDRAM total establishes capacity only; it does not validate the M7 timing numbers on GT-1.

The 7,980-byte `.namb` file can be stored separately; once loaded, one A2-Lite instance uses about 109.3 KiB for weights, instance data, and state at a 48-frame maximum, plus 12.4 KiB of engine code. A second distinct, concurrently prewarmed A2-Lite instance for a no-gap switch/crossfade would bring these working structures to about 218.5 KiB; engine code is shared, and two 7,980-byte model files would need separate persistent storage if both captures are retained. These estimates are small compared with the **24 MiB nominal external SDRAM** documented in the GT-1 service diagram (128 Mbit WORK plus 64 Mbit ERAM): about 0.45% for one engine's working data or 0.89% for two. The community-reported `M12L64164A` marking is a 64 Mbit part consistent with the ERAM capacity, though its exact IC reference/board revision is not verified. Total capacity is documented; free space, memory mapping, bandwidth, contention, and latency remain unknown. The upstream M7 benchmark places hot structures in DTCM and ring buffers in AXI SRAM; no equivalent GT-1 memory hierarchy or bus performance has been established. Capacity alone does not show NAM state can be placed or accessed within the audio deadline. Reproduce the size arithmetic with `python3 firmware/work/scripts/reproduce_nam_feasibility_estimate.py`; the output `firmware/work/nam-feasibility-estimate.json` records exact header-derived state bytes, rounded upstream struct sizes, separate code/capture storage, and nominal-capacity ratios.

**Model-data format comparison:** the pinned `a2lite.namb` sample validates locally as a 7,980-byte version-1 container with weights beginning at file offset `496`, `1,871` little-endian float32 values (`7,484` bytes) through end-of-file, sample rate `48,000.0`, and CRC-32 `0x7891AC48`. In contrast, three shared GT-1/GT-100 application islands have recurring 9-byte records containing two values that parse as float32 followed by `0xFF`; the observed chains contain 32, 23, and 21 pairs. This means those particular firmware spans are not laid out as a direct contiguous `.namb` weight array. It does not rule out a different internal numeric/table encoding, imply the spans contain NAM weights, or say whether firmware uses the values as floats. The exact hashes, CRC procedure, parsed model fields, table bytes, and parsed pairs are reproducible with `python3 firmware/work/scripts/reproduce_namb_gt1_numeric_format_comparison.py`; output is `firmware/work/namb-gt1-numeric-format-comparison.json`. The upstream reader source hash is recorded alongside the sample hash.

**Local benchmark toolchain gate:** a PATH-based inventory of this workspace environment finds only host GCC 15.2 targeting `x86_64-linux-gnu`; it finds no ARM/MIPS cross compiler, Clang/LLVM assembler, or QEMU ARM emulator among the checked commands. This is not a global search and does not rule out a proprietary Roland/Fujitsu compiler or ICE elsewhere. Because the MB8AA4181 ISA and application ABI are still unconfirmed, there is no known valid target configuration for building an informative NAM benchmark here. Host cycle timing would not answer the ESC2 feasibility question, and the published M7 numbers must remain comparator data. Reproduce the local tool lookup with `python3 firmware/work/scripts/reproduce_nam_toolchain_inventory.py`; its bounded findings and limitations are saved in `firmware/work/nam-target-toolchain-inventory.json`.

**Assessment: unknown; not demonstrated compatible.** Feasibility depends first on ESC2 ISA and compiler/toolchain support, then on measured per-block throughput, internal/external RAM layout and bandwidth, available program flash, and whether firmware exposes a safe insertion point. The 44.1 kHz versus 48 kHz mismatch is resolvable in principle with resampling or model adaptation, but it adds computational and latency costs requiring measurement.

## 6. Unresolved technical obstacles

1. All four officially listed releases (v1.05, v1.07, v1.08, v1.09) now have preserved packages and image hashes. v1.07 was fetched from a Roland-hosted URL using the documented naming pattern, but its archive URL is not linked from the current BOSS page.
2. The top-level image markers, hashes, sizes, and adjacent byte comparisons across v1.05–v1.09 are verified locally. The `+0x34` additive payload checksum is verified, but updater enforcement, compression/encryption, and full internal section boundaries remain undetermined.
3. ESC2's exact ISA remains unknown. Related AD-10 service documentation raises ARM Cortex-M as a moderate-confidence family hypothesis, but the GT-1 core variant, extensions, clock, core count, memory map, debug/programming access, and toolchain remain undetermined.
4. Ghidra includes ARM Cortex/Thumb languages, but use of one for ESC2 depends on confirming the ARM hypothesis and selecting the correct variant; a custom SLEIGH module may be needed if a different unsupported ISA is identified.
5. Nominal external SDRAM capacity is documented as 24 MiB, but available/free memory, bandwidth, contention, and latency are not measured; RAM shown in service notes may already be occupied by firmware/audio/effects.
6. NAM's 48 kHz assumptions and GT-1's 44.1 kHz audio rate need a concrete conversion strategy and end-to-end latency budget.
7. Existing amp-model block boundaries, audio callback/block size, floating-point format, and spare compute budget are unknown.
8. The image carries an additive payload checksum at each block's `+0x34`; whether the updater enforces it, any additional authentication, version rollback, failure recovery, and writable image regions remain unverified.
9. No physical extraction or hardware timing experiment has been performed; the user explicitly requires authorization before any physical GT-1 modification or flash operation.

### Bootstrap control-flow trace (static, v1.09)

The reset vector enters the trampoline at file `0xB14`; that trampoline branches to file `0x2F0`. At `0x2F0`, the code sets SP to `0x01028000`, calls setup at runtime `0x01000BB0` (file `0xBE0`), then branches through literal `0x010009F1`. Under the scoped map this enters the loader at file `0xA20` (runtime `0x010009F0`). The loader calls the callback validator at runtime `0x010009BC` (file `0x9EC`), selects section base `0x03002000` or `0x03040000`, reads its header, and calls decoder entry runtime `0x010008DA` (file `0x90A`). The section bases equal `0x03000000` plus file offsets `0x2000` and `0x40000`, where the matching GT1Upd and GT1Appli headers appear. The loader passes source=`base+[0x2C]`, destination=`[0x38]`, and output length=`[0x3C]`; on a zero output-length field it copies `[0x30]` bytes instead. Across all four preserved versions, the `[0x34]` word equals the additive byte sum of the bounded stored payload, confirming its checksum role.

The decoder initializes a 4 KiB ring at runtime `0x01010028`, uses runtime reader `0x010008C0` (file `0x8F0`), consumes control bits, literal bytes, and two-byte backreferences. The instruction-derived model consumes each bounded payload exactly and emits its `[0x3C]` length across all four versions. The updater output is identical across releases; the application outputs vary. In the loader, file `0xAC6` loads the selected header's `[0x28]` entry (`0x60000000`), and file `0xAC8` calls runtime `0x010002D4`. Under the scoped bootstrap map that call reaches file `0x304`, whose instructions are `ORR r0,r0,#1` and `BX r0`; this produces a static Thumb transfer to `0x60000001`.

The loader selection path is now bounded more precisely. The callback validator at runtime `0x010009BC` scans up to four 8-byte records through a pointer at `0x01010028`, invokes nonzero callbacks, and compares each return with the record's first word. It returns 0 on a mismatch/missing callback and 1 after all visited records pass. Loader return 1 selects the `GT1Upd` header at file `0x2000`; return 0 selects `GT1Appli` at `0x40000`. Runtime table contents and the meaning of validation remain unknown, so this does not establish the normal device mode.
Both decoded outputs share the first `0xE8` bytes. At output offset `0x7C`, the startup stub loads an entry pointer from `0x164` and branches through `BX r0` at `0x7E`. Its copy helper at `0x80` is called six times with literal descriptors; its zero helper at `0x9E` is called seven times. The first copied code segment is placed at `0x01000300`. The selected `0x0100xxxx` entry address falls inside that copied segment. That small trampoline writes `0x01000000` to a per-image address, loads SP through a per-image table address, and branches to a second target inside copied code. Across all four releases, the second target begins with a plausible Thumb prologue/call sequence for both updater and application. This cross-referenced transfer through decoded source bytes strongly supports the candidate load/copy map; it does not prove physical memory types or exact processor ISA.

## 7. Recommended next experiments

1. Trace incoming 0x11 read-request and 0x12 data-set frames through checksum/length validation, exact field layout, and ACK/error paths. The v1.09 receive state and response-builder trace is now reproducible; compare it with earlier application versions and official protocol documentation.
2. Resolve the normalized transfer ranges and `0x40100000`/`0x40100900`/`0x40100008`/`0x40100904` candidates against service documentation and schematics. Keep physical target and audio relationship unknown absent direct corroboration.
3. Follow the stable v1.08/v1.09 `0x600004A8` app dispatch and resolve its table source/callees, then pivot to reachable startup paths for audio initialization, sample/block scheduling, and amp/effect dispatch. The reproducible reference inventory is `firmware/work/gt1-02003-reference-probe.json`. Thumb-compatible control flow is supported for bounded entry paths, but the complete application ISA, exact ESC2 core, and physical load map remain unverified.
4. Obtain primary ESC2/MB8AA4181 architecture and programming documentation if possible. Continue cross-checking FA-08 ETM/audio labels, KTN-100 boot/debug nets, AD-10 trace signals, and GT-1 schematics. Keep the exact core/FPU/clock and debug access separate from ARM-family evidence; no physical debug or update experiments in this read-only phase.
5. Recover the audio path from static references: ADC/DAC setup, sample/block scheduling, buffer ownership and format, amp-model dispatch, effect-chain tables, latency and available RAM/bandwidth. Cross-correlate BOSS parameter/SysEx maps with code references only after image base and relocation are established.
6. NAM A2-Lite remains **not demonstrated compatible**. Its upstream M7 comparison is 4,059 cycles/sample at 48 kHz, with 102,468 bytes state at block 48, 12.4 KiB code, and 7,980-byte capture; GT-1 is 44.1 kHz. Once target/toolchain and audio deadline are known, compile a portable path and benchmark offline for the confirmed target, including resampling and existing effects. Do not use host timings or nominal SDRAM capacity as feasibility proof.
7. Keep all next steps read-only. Any write, update, bootloader test, risky board probing, or flash attempt requires separate explicit authorization; BOSS warns interrupted updates can require service.

## Tool and architecture status

Capstone 5.0.7 is available from the system Python environment. Coherent Thumb/Thumb-2 control flow and vector/literal references support a linear runtime mapping of `runtime_address = 0x00FFFFD0 + file_offset` for the first `ESC91.000` block; file offset `0x30` maps to runtime `0x01000000`, where the vector table begins. This mapping is limited to that block. It does not establish the execution ISA or load map for the later `BSSESC2:GT1Upd` or `GT1Appli` blocks. ARM/Thumb decoding of selected application offsets was inconclusive. A modulo-9 phase scan recovers the ARM Compiler C++ runtime diagnostic `SIGPVFN: Pure virtual fn called` across all four GT-1 app payloads and GT-1B v1.04, GT-100 v2.12, and KATANA v2.01/v4.00. The ignored nonprintable bytes recur at 9-byte strides, including markers other than `0xFF`/`0xDF` in GT-1 v1.05/v1.07 and GT-1B v1.04. The cadence resembles a separate candidate 8-data-bytes-plus-marker record pattern found elsewhere in app payloads; it could reflect record layout rather than an ordinary string section. Treat this as a repeated ARM Compiler runtime/data-layout clue, not proof of ARM execution, reachable code, or MB8AA4181 targeting. Image hashes, bounded spans, phases, skipped-byte positions/values, and raw-span hashes are recorded in `firmware/work/runtime-string-version-evidence.json`, generated by `python3 firmware/work/scripts/reproduce_runtime_string_versions.py`. See `firmware/work/updater-address-map-hypothesis.json` for the separate initial-block mapping anchors and limits.
