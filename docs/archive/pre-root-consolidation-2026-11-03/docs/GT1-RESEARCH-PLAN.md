# GT-1 NAM feasibility research plan

**Updated:** 2026-11-03  
**Status:** Active, static analysis only  
**Goal:** Determine whether one existing GT-1 amp-modeling stage can be replaced or augmented by NAM A2-Lite while retaining the processor's hardware and effects. Compatibility is unproven.

## Current position

The transfer/control path now has a reproducible protocol and four-version code comparison, but its physical target remains unknown and static service documentation does not map the candidate registers. Per the stopping rule, stop widening that search and prioritize reachable audio startup. The strongest new lead is the app's reachable pre-callback initialization at `0x600004A8` and its direct callees: before the 14-entry callback loop, code makes writes to several `0x400xxxxx` register blocks. These are confirmed setup writes, but their peripheral identities are unknown; no evidence yet ties them to audio. The `0x02003000` loader/runtime table and callbacks remain bounded leads: task/pool setup is established, while callback 10's optional handler only copies a global byte into an object field. No ADC/DAC, DMA, serial-audio, sample buffer, or amp-model execution path has been recovered.

The decoded app's second startup entry reaches `0x600004A8`. That routine loads `0x020030B4` as a base and makes indirect calls through offsets `-0x5C`, `+0x58`, `+0x70`, and `+0x7C`; the same route and call slots are confirmed in v1.08 and v1.09. Both versions call this dispatch before their 14-entry initialization callback loops. Four Thumb literal-load references in the bootstrap load base `0x02003000`, then call through offsets `+0x0C`, `+0x14`, `+0x18`, and `+0x58`. Ghidra call xrefs place these functions on the loader path: `0x010002CA` transfers to loader entry `0x010009F0`, which calls `0x01000B5E` and `0x010006D0`; `0x01000B5E` reaches `0x01000888`, which calls `0x01000862`. The bootstrap `+0x58` slot is exactly the app's `0x020030B4-0x5C` slot. GT-1B v1.04 has byte-identical code across bootstrap file offsets `0x700–0xBFF` and matching Ghidra references/call edges, supporting a shared boot interface. The inspected service-call function bodies dereference slots but do not directly write the table; a separate byte-copy helper exists in the loader, but its source/destination have not been tied to this table. Therefore the table's physical meaning, provider, initializer, and values remain unknown. A second app code sequence at `0x60000446` and an updater sequence at `0x60003ED2` also load `0x02003000` and call through `+0x0C`; startup reachability for these sites remains unproven. The app callback slots spanning `0x02003058` through `0x02003130` are outside startup ranges mapped so far.

In v1.09, the reachable route continues through `0x60000302`, `0x60000342`, `0x6000039E`, `0x6000046A`, and `0x60000440`. Its literal pool at decoded offsets `0x500–0x53C` includes `0x40007804`, `0x40025000`, `0x4002E000`, `0x40021184`, `0x4002D000`, `0x4002D800`, and `0x40023000`. Disassembly shows bit updates at the first group, writes through offsets `0x00/0x10/0x18/0x20/0x28/0x30` at `0x4002D000`, and configuration writes to `0x4002D800` and `0x40023000`. This is a reachable peripheral-initialization candidate. The addresses and ordering are observed; labels such as clock, audio, DMA, or codec are not established. The indirect targets from the `0x020030B4` slots remain unresolved. Check the v1.08 body instruction-by-instruction before treating the register writes as version-stable.

Ghidra 12.2 analyzes bounded copied regions as ARM Thumb-compatible code (`ARM:LE:32:v7`, Thumb context). This supports the ISA for those reachable paths only; it does not identify the exact MB8AA4181 core or prove its FPU, DSP extensions, clock, or full application ISA. The service notes document external WORK/ERAM capacities, but not available bandwidth or free memory.

The pinned TONE3000 A2-Lite implementation documents a 48 kHz engine and an upstream optimized Cortex-M7 result of 4,059 cycles/sample. GT-1 is documented at 44.1 kHz. These figures are comparison points, not GT-1 performance evidence. Neither compute fit nor a usable amp-block interface has been demonstrated.

## Work sequence

### 1. Resolve the dispatch base and recover the application map

1. Identify the source of the callable values at `0x02003000` before the loader path begins. Search the full bootstrap for writes/copies and compare other ESC2 product firmware/service-note maps; the same GT-1B boot code confirms a shared interface but does not reveal its provider.
2. Use the cross-product of bootstrap, app, and updater references to locate the provider and any initializer for the shared `0x02003000` region. The same `+0x58` slot appears in boot and app code; its actual pointer value is still outside the recovered images.
3. Follow the 14 app callback callees through their descriptor-table literals and helpers; determine whether their destinations or downstream calls reach peripherals, timers, buffers, or audio scheduling. Continue tracing the updater `+0x0C` candidate separately and keep reachability claims bounded to demonstrated call paths.
4. Resolve the app's indirect targets at `base-0x5C`, `base+0x58`, `base+0x70`, and `base+0x7C`; follow their callers and callees. Repeat with at least one earlier app version to distinguish stable framework code from changed product logic.
5. After identifying the region's source, return to the v1.08/v1.09 app callback paths and trace them toward audio initialization, sample scheduling, and amp/effect dispatch.
6. Produce a cited call graph from the second startup entry through initialization, event/task scheduling, and any candidate audio setup. Keep updater and app roles separate.

**Exit condition:** at least one reachable app path reaches a defensible audio initialization or processing schedule, or the exact static-analysis boundary is recorded with the hardware fact needed to proceed.

### 2. Find the audio processing and amp-model boundary

1. Follow references to converter, serial-audio, DMA, timer, interrupt, and buffer setup. Correlate firmware code with GT-1 service-note schematics, carefully distinguishing schematic facts from inferred firmware behavior.
2. Identify buffer addresses, sample format, channel count, frame/block size, callback cadence, effect ordering, and latency from code paths. Use parameter/SysEx maps only to associate controls with proven code references.
3. Trace the existing amp/preamp model dispatch and its inputs, outputs, state, scratch memory, calling convention, and deadline. Identify neighboring effects and shared resources.
4. If static evidence cannot establish a timing or electrical property, define a specific future measurement; do not infer it from nominal memory capacity or product labels.

**Exit condition:** an annotated integration boundary and scheduling contract, or a precise list of unknowns that require device-level observation.

### 3. Constrain the ESC2 target and resources

1. Seek primary MB8AA4181/ESC2 documentation and triangulate only with explicitly related products. Record evidence for core family, ISA revision, Thumb/FPU/DSP features, clocking, memory map, and compiler/runtime independently.
2. Map startup copy/zero ranges to physical memory only where schematics, linker clues, or code behavior support it. Estimate occupied and potentially free memory with uncertainty stated.
3. Bound memory access and execution budget from documented clock trees and firmware scheduling. If no defensible cycle budget is available statically, leave performance unresolved and describe the measurement required.
4. Determine whether Ghidra's ARM language is an adequate analysis language for the recovered paths; a custom processor module is only warranted if evidence shows instructions or semantics it cannot represent.

**Exit condition:** confidence-ranked target capability and memory/resource table; no architecture claim based only on tool selection or isolated instruction-looking bytes.

### 4. Test NAM against the recovered contract

1. Keep the embedded NAM revision and A2-Lite artifact pinned. Recheck the C fallback, compiler requirements, float behavior, model/state sizes, stack/scratch, and prewarm behavior against the recovered target.
2. Resolve 44.1-to-48 kHz conversion or a valid 44.1 kHz model path. Include both conversion directions if the surrounding GT-1 chain stays at 44.1 kHz, and account for buffering and latency.
3. Build a host/offline harness that mirrors the confirmed callback contract. Then, only with a supported target toolchain and reliable cycle method, benchmark the target implementation. Include conversion and the existing effects' remaining budget.
4. Compare the total cycles per callback and memory placement against a measured or defensible target budget. Label upstream benchmark data, modeled estimates, and target measurements separately.

**Exit condition:** feasibility marked feasible, infeasible, or unresolved with evidence and headroom. Do not claim compatibility without demonstrated compute and memory fit.

### 5. Update, recovery, and security questions

Static analysis has established section selection and decoded launch behavior, but the validator table, integrity algorithm, and supported recovery path are not fully explained. Correlate loader code with official update instructions and package structure; document checksum/signature evidence only when the exact bytes and verification path are identified. Do not test update failure, recovery, or flashing on a device during this phase.
